# Деплой PulsAura CRM в Cloudflare

Приложение работает целиком в Cloudflare Workers. Данные CRM хранятся в постоянной SQLite-базе Durable Object, изображения и резервные копии — в закрытом R2 bucket. Отдельный Node.js-сервер, VPS и D1 не нужны. Интерфейс, права доступа, личные пространства, задачи/подзадачи, воронки, встречи, импорт и интеграции сохранены.

## Быстрый запуск в интернете

Понадобятся Node.js 24, аккаунт Cloudflare и включённый R2: **Storage & databases → R2 → Overview → подключить R2**. SQLite-backed Durable Objects доступны на Workers Free и Paid; использование ограничено квотами выбранного тарифа. В конфигурации не выставлены платные лимиты CPU.

В терминале в папке проекта:

```powershell
npm ci
npx wrangler login
npm run cf:deploy
```

Если Cloudflare предлагает выбор аккаунта, выберите тот, где включён R2. Для однозначного выбора можно заранее задать `CLOUDFLARE_ACCOUNT_ID`.

Команда деплоя:

1. Создаст локальный `.cloudflare-secrets.json` со случайными секретами сессий и бэкапов и сложным паролем первого администратора.
2. Создаст закрытый bucket `pulsaura-crm-files` либо использует существующий.
3. Соберёт и опубликует Worker `pulsaura-crm`, создаст SQLite namespace и включит расписание.
4. Загрузит секреты в Cloudflare, определит публичный адрес `*.workers.dev` и проверит страницу входа.
5. При наличии токена бота настроит Telegram webhook и кнопку CRM.

Адрес будет напечатан в терминале. Логин по умолчанию: **admin@team.local**. Пароль находится в поле **SEED_ADMIN_PASSWORD** файла `.cloudflare-secrets.json`. Не отправляйте этот файл в GitHub и не удаляйте его между деплоями: он уже добавлен в `.gitignore`. После первого входа пароль можно сменить в профиле; seed больше не перезаписывает существующего пользователя.

Повторное обновление: `git pull`, `npm ci`, `npm run cf:deploy`. Данные и изображения сохраняются при обновлении Worker.

## Telegram и приём лидов

Без токена CRM работает, уведомления отключены. Для Telegram добавьте в `.cloudflare-secrets.json`:

- `TELEGRAM_BOT_TOKEN`: токен от BotFather;
- `TELEGRAM_BOT_USERNAME`: username без `@`.

Затем выполните `npm run cf:deploy`. Секрет webhook сгенерируется автоматически. Подключение аккаунтов через профиль, вход в Mini App, кнопки выполнения, уведомления о назначении/комментариях, напоминания и дайджест сохраняются. Уведомления помещаются в постоянную очередь; неудачные отправки повторяются по расписанию. Входящие webhook проверяются по секретному заголовку, повторные update_id отсекаются.

Для системы рассылок добавьте `OUTREACH_API_TOKEN` в тот же файл и повторите деплой. Endpoint остаётся `/api/outreach/events`.

## Собственный домен

В Cloudflare: **Workers & Pages → pulsaura-crm → Settings → Domains & Routes → Add → Custom Domain**. После подключения домена замените `APP_URL` в `.cloudflare-secrets.json` на `https://ваш-домен` и запустите `npm run cf:deploy`: ссылки и webhook будут обновлены.

Часовой пояс команды задаётся `TZ` в `wrangler.jsonc` (по умолчанию `Europe/Moscow`). Даты, календарные файлы и напоминания используют этот пояс, независимо от UTC среды Cloudflare и пояса браузера.

## Подключение GitHub в панели Cloudflare

Если предпочитаете автоматический деплой при push:

1. В R2 создайте закрытый bucket `pulsaura-crm-files`.
2. Создайте Worker из GitHub-репозитория `TesHokay/notes`, ветка `main`, корень репозитория.
3. Build command: `npm run cf:build`. Deploy command: `npx wrangler deploy`.
4. В **Worker Settings → Variables and Secrets** добавьте секреты `SESSION_SECRET` (32+ случайных символа) и `SEED_ADMIN_PASSWORD` (12+ символов). Добавьте `APP_URL` с публичным HTTPS-адресом Worker. Для операций бэкапа задайте секрет `BACKUP_ADMIN_TOKEN` (32+ случайных символа). Если страница ещё возвращает 503 из-за отсутствующих секретов, добавьте их и повторите deployment.
5. Для бота дополнительно задайте `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_SECRET` (24+ символа). Настройка webhook выполняется скриптом `scripts/configure-telegram.mjs` через локальный файл секретов либо официальным методом Telegram `setWebhook`.

Не используйте команду генерации локальных секретов как build command. При CI-деплое через `npm run cf:deploy` задавайте постоянные `SESSION_SECRET`, `SEED_ADMIN_PASSWORD` и `BACKUP_ADMIN_TOKEN` через секреты окружения CI.

## Локальная проверка версии Cloudflare

```powershell
npm ci
Copy-Item .dev.vars.example .dev.vars
npm run cf:dev
```

Адрес: http://localhost:8787. Локальный вход: `admin@team.local` / `local-admin-change-me`. `.dev.vars` используется только локально. Локальные данные Wrangler из `.wrangler/` не связаны с опубликованной CRM и не загружаются при деплое.

Проверки:

```powershell
npm run check
npm test
npm run cf:check
npx playwright install chromium
npm run test:cloudflare
```

Интеграционная проверка использует изолированную базу/R2 в `tmp/`, запускает браузерные сценарии и проверяет сохранение базы, изображений, импорта и ограничения входа после перезапуска. Производственные данные не затрагиваются.

## Резервные копии и перенос данных

Ежедневно и перед удалением клиента/пространства создаётся JSON-копия базы в закрытом R2. Ежедневно сохраняются последние 30 копий; отдельные операции хранят свои последние 10. Картинки лежат отдельно в R2 и при обновлении/восстановлении базы не удаляются.

Для вошедшего владельца с дополнительным заголовком `X-CRM-Backup-Token: <BACKUP_ADMIN_TOKEN>` доступны следующие административные endpoint. Этот отдельный секрет хранится в `.cloudflare-secrets.json`: полный бэкап содержит личные пространства, поэтому обычной роли владельца команды недостаточно для скачивания всей базы.


- `GET /admin/backups` — список копий;
- `POST /admin/backups` — создать копию вручную;
- `GET /admin/backups/<имя>.json` — скачать;
- `POST /admin/backups/restore` — multipart-поля `backup` (JSON-файл), `password` (текущий пароль владельца), `confirm=RESTORE`.

Перед восстановлением сохраняется ещё одна копия. Восстановление выполняется транзакционно и проверяет внешние ключи. После восстановления потребуется снова войти. Операция заменяет текущие записи базы данными копии.

Для переноса существующей SQLite-базы текущей версии CRM:

```powershell
npm run cf:export
```

Получится `data/cloudflare-export.json`; исходная база читается без изменения. Загрузите экспорт через endpoint восстановления после первого входа. При переносе с другого сервера также перенесите изображения из `public/uploads/feed/` в R2 с ключами `feed/<имя-файла>`.

Новый деплой начинает с новой базы и первого администратора. Файл SQLite из локальной папки автоматически в интернет не отправляется.

## Устройство и ограничения

Все обращения CRM идут в один SQLite-backed Durable Object `team-crm`. Это соответствует прежнему приложению для одной команды. Транзакции синхронные и атомарные; состояние импорта и ограничение попыток входа сохраняются в базе. EJS компилируется при сборке, без runtime eval. Статические ассеты не содержат пользовательские загрузки или секреты.

Один экземпляр базы подходит для небольшой командной CRM; при высокой нагрузке и приближении к квотам потребуется настройка тарифа/архитектуры. Бэкап и восстановление целиком сейчас рассчитаны на JSON до 20 МБ. Загружаемые изображения ограничены исходными 8 МБ, файлы импорта — 5 МБ. Для больших баз нужен потоковый перенос вместо полного JSON-снимка.

Логи: `npx wrangler tail`. Проверка пакета без публикации: `npm run cf:check`. Конфигурация ресурсов находится в `wrangler.jsonc`.

Официальные справочники: [Durable Objects SQLite](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/), [лимиты](https://developers.cloudflare.com/durable-objects/platform/limits/), [R2](https://developers.cloudflare.com/r2/get-started/), [Express в Workers](https://developers.cloudflare.com/workers/tutorials/deploy-an-express-app/).
